## Part 2 — Lecture Questions

**1. Define BOLA (API1:2023). Why is it the #1 API risk, and why can't a WAF reliably stop it?**

BOLA (broken object level authorization) is when an endpoint takes an object identifier from the client and returns or modifies that object without checking that the caller is entitled to *that* object. It is #1 because almost every REST API is shaped as `/resource/{id}`, the identifier is usually a guessable integer, and exploiting it needs no payload at all — a valid cookie or token plus one changed digit is a complete attack, so it survives every parser-aware defence. A WAF cannot stop it reliably because the request is *syntactically perfect*: correct route, correct method, well-formed body, no signature, no anomaly — the only thing wrong with it is a fact the WAF does not know ("does user 1 own order 3?"). That is business context, and it lives in the application's data model, so the fix has to be a per-object authorization check in the handler.

**2. What is mass assignment / broken object property level authorization (API3:2023)? Contrast a blocklist vs. an allow-list of bindable fields.**

Mass assignment is when the code copies whatever keys arrive in the request body into the record, so a client can set fields it was never meant to control (here `is_admin`, `balance`). It is "property level" because the same BOLA idea has moved down one level: not *which record* but *which field of that record*. A blocklist (`del body["is_admin"]`) has to enumerate every privileged field and fails silently the moment someone adds a new one — the default is "allowed"; an allow-list (`{k: body[k] for k in ALLOWED_CREATE_FIELDS}`) inverts the default so any key the developer did not name is ignored, which is the only version that stays safe as the schema grows.

**3. API4:2023 is unrestricted resource consumption. Give two distinct impacts (security and availability) of an unthrottled `/api/login`.**

Security impact: the endpoint becomes an unlimited password-guessing oracle — my run below got `401` six times and then a `200` on `alice123` with no cost, no delay, no lockout, which is exactly what credential stuffing and password spraying need. Availability impact: every request occupies a worker and a database/hash operation, so one client can exhaust the request pool and deny service (and inflate cost) for everyone else; it is also the amplifier for enumerating valid accounts.

**4. In `vulnerable_api.py`, `current_user()` trusts the `X-User-Id` header. Why is a client-supplied header NOT authentication, and what should replace it?**

Authentication has to be based on something the client cannot choose. `X-User-Id: 3` is just text the caller types, so "I am carol" costs one `-H` flag — a claim, not proof. What replaces it is an identity that is minted and verified server-side: a signed session/token (JWT signed with a server-side key, or an opaque session id looked up in a store) where the server derives the user id from the verified credential instead of reading it from the request.

**5. Why does object-level authorization have to be checked per request, per object rather than once at login?**

Because login only answers "who are you"; it says nothing about *which* records that identity may touch, and that answer depends on the object — its owner, its tenant, its sharing state, its lifecycle — all of which change while the session is alive. The object id is also attacker-chosen on every single call, so each call is a fresh authorization question; a check made once at login is a snapshot taken before the attacker picked the id.

### Task 1 — BOLA: read another user's orders (API1:2023)

```console
$ curl -s http://localhost:8080/api/users/3/orders
[{"item":"Server rack","order_id":"C-1","total":5000},
 {"item":"FLAG{bola_demo}","order_id":"C-FLAG","total":0}]          [HTTP 200]
$ curl -s http://localhost:8080/api/users/2/orders
[{"item":"Mouse","order_id":"B-1","total":15}]                      [HTTP 200]
```

No credential of any kind was sent: the handler is `return jsonify(ORDERS.get(uid, []))` (`vulnerable_api.py` L49–51) — the id in the path *is* the authorization.

Secure API ladder — the status code is the lesson:

```console
$ curl -i http://localhost:8081/api/users/3/orders                       -> HTTP/1.1 401 UNAUTHORIZED   (no identity)
$ curl -i -H "X-User-Id: 1" http://localhost:8081/api/users/3/orders     -> HTTP/1.1 403 FORBIDDEN      (alice -> carol's orders)
$ curl -i -H "X-User-Id: 1" http://localhost:8081/api/users/1/orders     -> HTTP/1.1 200 OK             (alice -> her own)
$ curl -i -H "X-User-Id: 3" http://localhost:8081/api/users/1/orders     -> HTTP/1.1 200 OK             (carol, admin -> alice's)
```

The fourth line matters: the fix is **not** "always 403 for a foreign id", it is "owner **or** explicitly privileged", which is why the check is `if caller["id"] != uid and not caller["is_admin"]` (L51) — an `or` in business terms, an `and`-with-negation in code.

**Mitigation:** object-level authorization — resolve the caller from a verified credential and compare it to the object's owner (plus an explicit admin branch) before serialising. API1:2023.

### Task 2 — Mass assignment: self-promote to admin (API3:2023)

```console
$ curl -X POST http://localhost:8080/api/users -H "Content-Type: application/json" \
    -d '{"username":"mallory","password":"x","is_admin":true,"balance":1000000}'
{"balance":1000000,"flag":"FLAG{massassign_demo}","id":6,"is_admin":true,
 "password":"x","username":"mallory"}                                     [HTTP 201]
```

Both smuggled fields bound, and `is_admin:true` additionally released the flag (`vulnerable_api.py` L62–64: `user.update(body)` then `if user.get("is_admin")`). Against the secure API the same body is neutered:

```console
$ curl -X POST http://localhost:8081/api/users ... -d '{...,"is_admin":true,"balance":1000000}'
{"balance":0,"id":6,"is_admin":false,"password":"x","username":"mallory2"}   [HTTP 201]
$ curl -X POST .../api/users -d '{"username":"onlyname"}'
{"error":"username and password required"}                                  [HTTP 400]
```

The second secure call is the edge case an allow-list alone would miss: with only `username` supplied, allow-listing would happily create a half-built user, so `solution_api.py` L62–66 also validates required fields before forcing `balance: 0, is_admin: false`.

**Mitigation:** bind an explicit allow-list of client-settable fields (`ALLOWED_CREATE_FIELDS = {"username","password"}`, L34) and let the server own `id`/`is_admin`/`balance`. API3:2023.

### Task 3 — Unrestricted resource consumption: brute-force login (API4:2023)

```console
=== :8080 (insecure) — every attempt is processed ===
attempt pw=wrong1    -> 401
attempt pw=wrong2    -> 401
attempt pw=wrong3    -> 401
attempt pw=wrong4    -> 401
attempt pw=wrong5    -> 401
attempt pw=wrong6    -> 401
attempt pw=alice123  -> 200        {"is_admin":false,"ok":true,"user_id":1}

=== :8081 (secure, RATE_LIMIT=5 / RATE_WINDOW=60s) ===
401 401 401 401 401 429 429
--- 429 body: {"error":"too many requests"}
```

Seven guesses cost nothing on `:8080` — and one of them was the password. On `:8081` the sixth attempt in the window is refused (`solution_api.py` L73–90: per-IP list of timestamps, pruned to `RATE_WINDOW`, `429` when `>= RATE_LIMIT`).

**Mitigation:** server-side throttling with a bounded window (plus per-account counters and backoff in real systems), so guessing becomes slow and loud instead of free. API4:2023.

## Part 4 — Reflection

**1. Mapping table**

| Finding | Endpoint | OWASP API id | Fix applied |
|---|---|---|---|
| Read carol's orders (incl. `C-FLAG`) anonymously | `GET /api/users/<uid>/orders` | API1:2023 BOLA | per-object ownership check + 401/403 + admin branch (L47–52) |
| Self-promotion to admin with balance 1000000 | `POST /api/users` | API3:2023 mass assignment | allow-list binding + server-owned sensitive fields (L34, L62–66) |
| Unlimited password guessing (found `alice123` on the 7th try) | `POST /api/login` | API4:2023 | per-IP sliding-window limiter → 429 (L73–90) |
| Identity taken from `X-User-Id` | all | API2:2023 (broken authentication, supporting all of the above) | design note only — this lab's "secure" build still trusts the header; a verified token would replace it |

**2. Real breach.** I used the **Optus (2022)** exposure: an unauthenticated API endpoint keyed by sequential customer id returned name, DOB, address, passport/licence numbers, and enumerating the id range walked the whole customer base — the pattern is API1/BOLA, not a leaked password. The `solution_api.py` check would have stopped the *authorization* half (id 3 asking for id 1's orders returns 403), and it generalises: an owner comparison on every object read is exactly what was missing. It would **not** have stopped the underlying enumeration problem on its own — the API still needed real authentication in front of it, rate limiting, and non-sequential ids; the ownership check is necessary, not sufficient.

**3. Best mitigation.** Object-level authorization is the highest-leverage control for an API platform: it is the one that closes the #1 risk, it is cheap per handler, and it is the only one that stops an attacker who already holds a *valid* account — which is the normal situation in a breach. Allow-list binding and rate limiting are strong but narrower (schema-dependent and volume-dependent). The honest ranking is: object-level auth first, then allow-list binding on every write endpoint, then throttling — with the caveat that all three sit behind real authentication, because none of them can help while `X-User-Id` is the identity.

- **Explain in my own words — why the fix holds / what could still break it:** the ownership check holds because it compares the caller's verified identity to the object *at request time*, so a guessed id has nothing to bypass; but it is only as good as the identity — while `X-User-Id` is trusted, anyone can become carol (`-H "X-User-Id: 3"` is literally how I reached the 200 above), and the same applies to the admin branch, which is now a header away from being forged. The rate limiter holds per process and per IP: restarting the API (or running N workers) resets the budget, and an attacker with rotating IPs defeats it — so it must be backed by per-account counters and a shared store.

## 🤖 Audit the AI

**1. The AI's answer (verbatim, from this assistant's suggestion).** Asked to "fix the BOLA flaw in `vulnerable_api.py`", it produced this:

```python
@app.get("/api/users/<int:uid>/orders")
def get_orders(uid):
    if int(request.headers.get("X-User-Id", 0)) != uid:
        return jsonify({"error": "forbidden"}), 403
    return jsonify(ORDERS.get(uid, []))
```

and for mass assignment it advised adding this line to `create_user()`:

```python
body.pop("is_admin", None)   # strip privileged fields
```

**2. What is wrong with it.**
- `int(request.headers.get(...))` is called **outside** any `try`, so `X-User-Id: abc` raises `ValueError` → a 500 instead of a 401. The lab's own `current_user()` wraps exactly this conversion (`vulnerable_api.py` L41–43) and the AI dropped the guard.
- It treats *no header* as id 0 and returns **403** rather than **401** — "you may not" and "I don't know who you are" are different answers, and collapsing them hides missing auth from logs and monitoring. My verified ladder shows 401 for no identity and 403 only for a real, wrong-owner caller.
- It hard-requires `caller == uid`, which **breaks the admin case** it never considered: carol (id 3, admin) reading user 1's orders returned **200** on the real secure build, and this "fix" would 403 it. A plausible-looking security patch that silently breaks a legitimate feature is the cheapest way to get the check removed again later.
- The mass-assignment fix is a **blocklist**: it names `is_admin` and forgets `balance` — which is the field I actually set to 1000000 — and it would miss any privileged column added later (`role`, `email_verified`, `credits`).
- Neither snippet validates required fields, so allow-listing (if adopted) still creates half-users — the real build returns **400** for a body with no password.
- The AI also asserted the offset/parameter was "done" without running anything; nothing in its answer is accompanied by a request that proves the exploit now fails.

**3. The corrected version I verified myself** is `solution_api.py`'s three blocks — `caller is None → 401`, `caller["id"] != uid and not caller["is_admin"] → 403`, `ALLOWED_CREATE_FIELDS` + forced `balance/is_admin`, and the windowed limiter — with the status codes I actually observed (401/403/200 for the ladder; 201 with `is_admin:false, balance:0`; 401×5 → 429). The AI's output was insufficient because it patched the *symptom it could see* (the id in the URL, the one field in the news) instead of the mechanism (server decides identity, fields, and volume), and it never ran the exploit after the fix.
